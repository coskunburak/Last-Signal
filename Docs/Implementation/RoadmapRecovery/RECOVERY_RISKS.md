# Recovery risks

The original persistence absence and pickup callback hazard have implemented fixes; acceptance depends on the separate final gates. Initial failure XMLs are retained.

- Current persistence is a small single-world, living-checkpoint foundation. No two-cell streaming, death recovery, content migration or polished save UI is certified.
- Load is menu-only. Invalid files do not create a session. Hydration failures return to menu and preserve the disk source. Capsule overlap is checked; broader streaming/location suitability remains a future contract.
- File publication uses flushed candidates and same-directory replacement with backup. Injected failures prove prepublication preservation, not physical power-loss durability or Windows behavior. No cross-process concurrent writers are supported.
- Capture is explicit and scene-scoped; current-world performance does not predict release-scale scenes. Allocation counters without reliable calibration cannot establish zero allocation.
- Current catalog has six resource definitions, no unique equipment payload or mass authority. Required unknown definitions reject load. Catalog breadth, weight and melee remain open product scope, not silently removed requirements.
- Existing tests write historical evidence and Unity normalizes material defaults. Preserve those run outputs in recovery evidence and restore only confirmed generated differences.
- Automated fixture routes are not human playtests. External pilot and Windows certification remain unverified.
